### 为什么没有直接通过在线命令升级

测试时 v1.3.4 的 GitHub Release 和 Tag 均已删除，返回 404。在线向导无法取得原正式版基线，因此在替换程序之前安全停止；这不是实例已损坏，也不是升级成功。

用户随后明确授权核验原提交、备份并人工升级。本次从留存的不可变 Git 对象取得原版源码，使用正式 v1.4.2 的原有基线校验逐项比对 **99 个受管载荷文件**，确认匹配后再运行升级。目标来自已发布的 v1.4.2 源码资产，校验 SHA256 清单并通过源码包验证：

```text
TG2Cloud-v1.4.2-source.tar.gz
SHA256: 1942b306a0e96e3c81119aa7edf7951acc3d63cb9d854165ab224db14dba3016
```

人工编排调用正式版原有计划与执行核心，保留实例归属、容量、源码、候选镜像、数据库快照、切换、健康与 HTTPS 检查；没有改版本号、关闭指纹校验、添加强制覆盖参数或改写正式资产。另安装同版离线 `tg2cloud` 管理工具，来源如实记录为本地核验的正式源码。

**此记录证明人工核验后的这一次升级完成，不证明“原 Release／Tag 已删除”的在线自动升级路径已修复。** 公开脚本遇到同类缺失仍会停止，不提供通用的绕过命令；应保留服务和数据，单独审阅可追溯基线及维护方案。

## 备份与维护边界

- 升级前检查无活动任务；配置、Compose、版本身份、rclone 配置和必要网关配置在 VPS 私密目录备份，归档清单及校验和已核验。
- 业务数据库和 Telegram Session 使用 SQLite 一致性备份并检查完整性；网关中识别出的 SQLite 文件也走 SQLite 备份。其他在线网关配置仅作为参考副本，不宣称是网关全部状态的停机一致快照。
- 共享代理另用现有备份工具创建归档，完成核验和隔离目录解包演练。解包可用不等于已覆盖运行服务、验证灾难恢复。
- 暂存文件保留原位并比对清单；没有递归复制网盘挂载、清理失败文件或删除历史回退点。此次备份保留在测试机，不放入 Git 或公共报告。
- 原升级器另创建配置回退点和一致性数据库快照，保留旧 Bot 镜像；未注入故障或执行回退恢复。
- 只切换所选 Bot。基础安装步骤更新了宿主 CA 证书包，不据此宣称宿主系统逐字节不变；Docker daemon、网关和共享代理未重启。
