# 文件命名与媒体组说明

本文是命名规则的详细入口。适用于 CloudDrive2 和 OpenList 共用的 Bot 核心，不改变下载、上传、去重和远端冲突处理。日常命令见 [Bot 使用指南](BOT-USAGE.md)，结果不确定时见[恢复指南](RECOVERY.md)。


## 来源命名与人工修正（v1.4.9）

新增兼容／说明优先／字段模板方案，兼容模式默认不改现有有效原名优先；待确认卡片可仅修改本次，来源规则须明确保存。目录和规则在接收时冻结，成员各自季集不按顺序猜测。步骤见[监听与转存计划](LISTENING.md)。

## 原名、说明和自定义名称的关系

1. 单独发送图片或视频时，先保留已有语义的原文件名，例如 `The Last Journey.mp4`。
2. 无原名、数字名、默认 video/VID／photo/IMG 编号、长十六进制、明显混合随机 ID 或网址／账号污染名，才尝试用可靠说明替换；处理前缀不等于所有英文原名都无效。
3. 从本条实际送达的文字产生候选，清理网址、账号、话题和推广，按可读性及明确标题／集数等线索选择。
4. 没有可靠候选或提取异常时，使用安全原名；无原名则沿用 `telegram-消息编号.扩展名` 等兜底，不因此丢弃文件。
5. 完整媒体组采用统一标题时，是单独的组命名规则，会覆盖该组新视频／图片原有名称；原名仍存入任务记录。

这不是“所有视频都按 caption 改名”。直接发送一个已改好文件名的视频，是保留指定名称的可靠方式；当前没有“给旧任务补发文字便自动改名”的功能。

## 程序实际能看到什么

| 来源 | 是否用于命名 |
| --- | --- |
| 视频自己的原始文件名和类型元数据 | 是。 |
| 本条消息实际送达的 caption／文字 | 是，包括可见的引用块。 |
| 经过身份、私聊和组编号核对的同组说明 | 是，仅本次收到的组成员。 |
| 只在来源频道另一条消息或评论区出现的说明 | 不自动取得。 |
| 转发来源的频道名称 | 不拿来猜文件主题。 |
| 视频画面、语音、网址对应网页 | 不做 OCR、语音识别或联网抓取。 |

Telegram 客户端有时只转发了单个视频，没有把相册图片上的说明一起带来。Bot 无法恢复未收到的文字。可转发整组，或给视频添加自己的说明后发送；受保护内容不绕过限制。

## 多语言与候选选择

支持中文、繁体、日语、韩语、英文、重音字母和其他 Unicode 文字，不简单按“中文优先于英文”排序。

- 明确的 `标题：`、`Title:`、`題名：`、`제목：` 等标签提供较强线索。
- 集数、年份、版本号保留，例如 `三体 第12集`、`One Piece 第1080集`、`Python 3.12 v1.2.0`。
- 可读的引用块和完整描述比笼统的“本期推荐”更有价值。同分候选保持来源顺序，不只挑最长的一行。
- 明显的段落续行可合并，空行、推广和链接边界不当作同一段。过长描述尽量在分句／词边界取片段，再遵守字节上限。
- `标题：1984`、`《1917》` 有作品语境，可作为数字标题；任意孤立数字不自动当作品名。
- 随机串识别保持保守；短纯字母串可能是生僻作品名，不靠猜测强行覆盖。

## 过滤与文件名安全

清理明文网址、常见裸域名、隐藏链接标签、`@账号`、`#话题`、邮箱、推广／引流以及密码、提取码、大小和纯画质信息。标题和账号在同一行时尽量保留真正的标题，不简单删掉整行。

`Node.js`、`ASP.NET` 等技术名称有保护规则，但域名判断不是完整公共后缀库；生僻网址、标题与域名无分隔粘连时仍可能存在歧义。

Telegram 的隐藏链接、代码、剧透等实体继续按既有策略遮蔽，不能把“界面可见”理解为所有实体文字都会进入标题。实体偏移按 Telegram 的 UTF-16 单位处理。

最终名称统一清理控制字符、非法路径字符和危险路径，规范化 Unicode，限制为最多 180 个 UTF-8 字节；中文字符不是按一个字节计算。扩展名依附件／原名处理，不根据说明中的 `.exe` 等字样改变文件类型。

例如 `三体：黑暗森林 第12集` 的冒号会替换，实际可得到 `三体_黑暗森林 第12集.mp4`，不是保留所有标点原样。

## 完整媒体组

同一次转发包含图片、视频和说明时，从已验证的本组说明评分选择标题。例如：

```text
城市夜景-图片01.jpg
城市夜景-视频01.mp4
城市夜景-视频02.mkv
```

上例多成员的图片／视频各自编号，保留各自扩展名；普通文档不套用图片／视频统一命名。v1.3.4 起，同组恰好一图一视频且真实后缀可区分时不加种类编号，见[图片／视频同名](#说明正文与图片视频同名待发布)。同类、更多成员或无法区分后缀时继续编号。组成员按消息编号稳定排序，重复更新不产生新任务。

Telegram 分批投递时会短暂等组；只收到单个成员约 2 秒后按单条规则处理。迟到说明不会回头改写已经登记的任务，也不会借用上一组文字。任务接收顺序和回复顺序可能不同，以任务编号及实际文件为准。

## 例子：正式版既有能力

以下假设附件为视频，扩展名为 `.mp4`，且没有重复任务：

| 原名 | 实际收到的说明 | 预期规则 |
| --- | --- | --- |
| `12345.mp4` | `三体 第12集` | `三体 第12集.mp4` |
| `Ab83Kd91X.mp4` | `오늘의 여행` | `오늘의 여행.mp4` |
| `12345.mp4` | `君の名は。 君の名は` | 清理重复标题，使用 `君の名は.mp4`。 |
| `The Last Journey.mp4` | 另一段描述 | 保留原名。 |
| `12345.mp4` | 只有网址、账号和广告 | 保留安全原名。 |
| `12345.mp4` | 根本没有说明 | 不猜主题，保留原名。 |

重名时仍由原有目标路径预留与任务后缀规则处理；本页的示例不承诺覆盖已有同名文件。

## 待发布修复

以下增强已随 v1.3.4 正式发布，需实际升级 Bot 后生效；v1.3.3 不包含这些修复。保留本节旧标题仅用于兼容链接，不表示仍未发布：

- 以 `/` 开头的媒体说明不再被当成纯文字命令而跳过文件。文字 `/start` 等命令仍正常。
- `广告狂人`、`大小谎言`、`密码疑云`、`Password to Paradise` 等正常作品名不因前缀误杀；格式化密码、容量、时长等字段仍过滤。
- 表情后的 `🎬 标题：星际穿越` 保留明确标题优先级。
- 同条说明中相邻的 `三体` 与 `第12集` 可得到 `三体 第12集`，但不跨空行、推广／链接边界或多条无关消息拼接。
- `AC/DC Live 2026` 安全保存为 `AC_DC Live 2026.mp4`，不丢掉斜杠前面的文字；原始路径的安全处理不放宽。
- 改善紧贴中文的 ASCII 域名及尾部画质标签清理，例如 `三体 第12集.mp4 [1080P]` 不再叠加错误扩展名。
- 视频附件元数据明确而原名后缀为 `.exe` 等明显不符时保守修正；正常 `.MKV` 等原视频后缀优先。不做文件内容嗅探，也不把 MIME 当作内容完整性验证。

这些修复与下节图片规则一起纳入 v1.3.4，不改名历史任务，不增加依赖、配置或数据库迁移；本版真实 Telegram／两版网关仍需后续验收。

### 说明正文与图片／视频同名（待发布）

本节已于 v1.3.4 发布，“待发布”仅为保留原链接锚点，不是当前发布状态。

针对 `processed_www.example.test@原片段_编号.mp4` 这类被网址或处理信息污染的原名，不再要求同时含有“关注／频道”等推广关键词，才允许分析本条有效说明。`processed_123456` 等默认处理编号也可替换；普通有语义的名称、真正讨论某网站的教程标题和 `Processed Memories` 不机械删除。

单张图片也可以使用**自己的**说明：无原名、数字／IMG 默认名或受污染原名有可靠正文时，用正文生成安全名称；正常照片原名优先，无说明仍沿用原有兜底。音频、PDF 和其他非图片／视频文档不新增说明改名。

同一已验证媒体组**恰好一张图片与一个视频**，且实际扩展名不同，可生成：

```text
城市夜景旅行记录.jpg
城市夜景旅行记录.MP4
```

扩展名及其大小写按实际附件规则保留，不强制将 `.mp4` 改为 `.MP4`。两个视频、两张图片、更多成员或无法区分扩展名时仍保留种类／编号；远端重名保护不取消，绝不靠覆盖同名文件实现统一标题。

只处理消息实际送达的有效文字，过滤网址、话题及账号，保留必要空格并按既有规则规范化标点；超长说明仍遵守 UTF-8 字节限制，不承诺逐字符照搬整段。已登记任务不追溯改名；图片与视频分开发送、其中一条没有说明时，不擅自关联另一条文字。

## 如何验收和反馈

维护采用[样例驱动](development/MAINTENANCE-NEXT.md#4-命名只做可验证的小步改进)：先补合成或脱敏回归，核对名称和来源，再决定是否改规则。本轮只扩充多语言与广告边界样例，既有原名优先、媒体组和安全回退不变。

先在自有可重复获取的测试文件上核对接收提示，再查看 `/task 编号` 中的原名和当前名，最后核对 WebDAV 中实际文件。分别测试单视频、完整媒体组、无说明和有语义原名，不反复向同一文件盲目重发。

报告识别问题时，只提供脱敏后的原文件名、实际送达的说明、是否为媒体组、Bot 实际版本及接收名称。不要提供私人视频、Token、Session 或完整日志。没有送达的评论和视频画面文字不属于可直接利用的命名输入。
