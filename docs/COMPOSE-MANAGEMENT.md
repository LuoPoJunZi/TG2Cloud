# Compose 统一管理与安全维护

本页适用于 **v1.5.8 format 3 完整部署包**，v1.5.7 旧包没有 `manage.sh`。版本、镜像、两 Edition 部署包和校验清单核验齐全后再使用，发布状态见[本版记录](development/V158-ACCEPTANCE.md)。安装教程见 [Compose 安装](COMPOSE.md)，不能只从 main 复制一个脚本到旧实例。

## 管理入口

新版 format 3 部署包包含 `manage.sh`，与 `https.sh` 共用随包的、带哈希清单的离线 Python 工具。宿主需要 Linux、Python 3.10+、Bash、本机 Docker Compose 和 root 权限；无需在宿主安装 Telethon 等 Bot 依赖。帮助、状态和管理不会每次下载 main。

在实际 Compose 部署目录运行：

```bash
bash manage.sh
```

从其他目录调用也可以，例如：

```bash
bash /opt/tg2cloud-compose-openlist/manage.sh
```

新工具安装到独立宿主 CLI 后，也可使用 `tg2cloud compose --root /实际部署目录`。不会默认覆盖已有脚本实例的 `tg2cloud` 快捷命令。没有安装该 CLI 时使用部署包内的 `manage.sh` 即可。

```text
1.  安装与升级
2.  查看运行状态
3.  查看运行日志
4.  服务启停管理
5.  Bot 用户管理
6.  WebDAV 凭据
7.  HTTPS 与管理
8.  文件分类设置
9.  异常通知设置
10. 业务就绪检查
11. WebDAV 验收
12. 故障诊断报告
13. 数据备份管理
14. 卸载当前实例
15. 外部 WebDAV
16. 监听管理
17. 资源与安全
0.  退出
```

首次尚未初始化时，菜单调用原有隔离 `setup` 服务逐项填写；该服务不挂载 Docker Socket。先启动并配置网关，在后台完成云盘挂载和专用 WebDAV 账号，再启动 Bot。已有 `.env` 不重新生成。

## 和一键脚本的关系

| 能力 | Compose 新管理工具 |
| --- | --- |
| 任务、命名、转存、家人权限、分类、通知、监听 | 使用同一 Bot 和公共管理服务，保留原有鉴权与恢复保护 |
| 查看状态、日志、凭据、诊断和业务就绪 | 菜单可用；只读检查与写入验收分开 |
| 监听账号登录、状态、停用 | 菜单可用；个人 Session 与 Bot Session 分开，不重启 Bot |
| HTTPS、Certbot、代理备份 | 复用受管共享代理；不启动第二套争抢 80/443 的代理 |
| 外部只读 WebDAV | 菜单可用；要求网关绑定回环地址、身份核验通过，继续使用独立只读账号与目录隔离 |
| 已有第三方 Nginx／外部代理 schema 3 | 保留导出候选配置方式；尚不自动接管该代理，也不支持在该模式发布 Compose 外部 WebDAV |
| 安装 Docker、系统软件或配置防火墙 | 仍由用户按平台文档准备，不调用主安装器接管宿主 |
| 升级、备份、卸载 | 使用 Compose 专用生命周期和归属校验；不冒充脚本实例 |

同一 Edition 的脚本与 Compose 仍不能共用固定容器、网络、Token 或数据目录。工具拒绝未知容器、改写过的基础 Compose、额外 override、路径链接和不匹配的挂载。自定义 Compose、NAS 的远程 daemon 或非标准网关不是自动接管目标。

## 为什么任务一直排队

容器存活不等于下载已放行。新版本业务就绪会输出有效可用内存、下载保护门槛、容器内存上限、下载／上传窗口和全局等待原因；诊断另按固定类别统计排队任务的重试等待、个人额度、暂存额度和真实磁盘空间等待，不输出文件名或凭据。

内存采样兼容标准 Docker cgroup v2 和 v1 内存控制器，取宿主可用内存与容器有效余量中较小的一项。低于保护门槛时，业务就绪不会再把下载资源标记为通过。无法读取受支持控制器时退回宿主采样；复杂的嵌套 cgroup、NAS 资源管理仍需结合实际容器限制核对。

先从菜单查看“业务就绪检查”和“故障诊断报告”，再在 Bot 查看具体任务详情。不要通过降低保护门槛、删除数据库或无限增加并发来消除排队。旧 Bot 没有新观察字段时显示“未核实”，不推断它已通过。

## 凭据与资源保护

新版 Compose 明确列出允许进入 Bot 的配置；OpenList 首次管理员密码只交给网关，不再通过整份 `.env` 进入 Bot。主机 `.env` 仍有明文／Base64 配置，Base64 不是加密，保持 root 所有、600 权限；已有旧容器必须通过完整新版部署包重建后才应用隔离。

Bot 默认限制为 256 个进程／线程。CPU 和内存硬限制默认不设置，避免对不同配置强套过小上限。“资源与安全”允许设置：

| 项目 | 配置键 | 含义 |
| --- | --- | --- |
| Bot 内存 | `TG2CLOUD_BOT_MEMORY_LIMIT` | `0` 不限制，或 `1024M`／`2G`；至少高于下载硬门槛 256 MiB |
| Bot 进程／线程 | `TG2CLOUD_BOT_PIDS_LIMIT` | 默认 `256`，可设 32～65536 |
| Bot CPU | `TG2CLOUD_BOT_CPUS` | `0` 不限制，或如 `1`、`0.5` |

应用前须暂停调度、等待活动传输结束，确认后仅重建当前 Bot。旧配置保留为私有 `.env-before-resources-*`，工具读取 Docker 实际限额核对；核对失败不声称生效或自动回退。硬内存上限仍可能导致 OOM，应为 Python、rclone 和缓冲留足余量；此处不限制网关全部缓存。

CloudDrive2 的 FUSE、特权和宿主进程可见性保留原方案；它依然是高信任组件。本轮未宣称已将这些权限安全移除。OpenList 保留非 root 和已有权限限制。两种部署的日志轮转和 Bot 非 root 保护继续保留。

默认管理端口仍仅回环监听，内网绑定只用于可信局域网。不要暴露 19798／5244 公网端口。Docker 版本、宿主安全更新和 NAS 的端口转发需另行维护；工具不会修改 daemon 或开放防火墙。

## 升级与失败处理

1. 在菜单暂停新任务，等待活动下载、流式、上传及清理结束。
2. 选择“安装与升级”，填写正式稳定版本，或回车选择最新稳定版。
3. 工具核对官方 Release、同版 Compose 包校验清单、工具文件、镜像 digest、Edition 和不可变提交。资产缺失或校验失败时停止，不回退 main。
4. 确认后停止当前 Bot，创建包含配置、业务数据库、Bot／个人 Session 和网关授权的一致性快照，再拉取候选镜像并切换当前 Edition；另一 Edition 保持原状。
5. 原 `.env`、数据库、Session、下载、日志及网关数据保持原路径。升级后继续保留暂停状态，由用户完成业务验收再恢复调度。

新 Bot 启动前失败时，工具尝试恢复旧部署文件和原运行状态，并核对是否恢复；恢复未确认会保留事务记录。**新 Bot 可能启动并写入数据库后，失败会停止它并标记待核实，不自动用旧库覆盖新库，也不自动启动旧代码。**

`.compose-upgrade.json` 记录版本、阶段和本地快照路径，不含密码。遇到 `needs-review` 或未完成事务，先保留全部数据，按 [备份与恢复](BACKUP-RESTORE.md)核对快照、代码、数据库版本及消息处理范围，不删除记录后盲目重跑。

带完整 `https-tools/` 的历史 format 2 包按旧版自己的哈希清单和 Compose 模板核验。旧包没有 `manage.sh` 时，先在旧 Bot 发送 `/pause` 并等待活动任务结束，再下载、核验完整 v1.5.8 新包，用新工具指定旧实例目录，例如 `bash /新包/manage.sh --root /旧实例目录`。旧 Bot 不支持新宿主暂停接口。这不修改旧包的 helper，也不执行下载的旧源码提取版本。请先核对本版资产已经完整发布。

早期 format 1 包没有离线工具，不能使用上述菜单自动升级；新工具会明确停止。按原 [Compose 教程](COMPOSE.md)完整备份、核对新旧配置与镜像，并保留原数据和两个 Session；不要仅复制一个新脚本或伪造部署包标记。

## 备份、加密与恢复预检

“数据备份管理”可以创建实例快照、隔离恢复预检、加密现有备份和单独备份共享代理。实例备份不含云端文件、下载、日志、共享证书；代理证书另备份。快照包含敏感授权，默认保持本机私密权限。

加密副本需要宿主已安装 GnuPG 与 gpgconf，工具不自动安装、不向 Bot 添加依赖。口令隐藏输入两次，仅通过 stdin 交给 GnuPG，AES256 加密后先解密回读验证再发布 `.gpg` 副本；原明文归档保留，不自动删除。密码请另存密码管理器，再把加密副本离机保存。

恢复前，在私密目录解密，之后运行菜单的“隔离恢复预检”。例如宿主 GnuPG 交互解密时：

```bash
umask 077
gpg --output /私密目录/恢复检查.tar.gz --decrypt /私密目录/备份.tar.gz.gpg
```

归档结构和数据库通过不等于能恢复服务。正式恢复必须先保护现有配置、停止旧实例，使用匹配版本，避免两套相同 Bot Token／Session 同时处理消息。本菜单不提供会覆盖生产数据库的一键恢复。

## 停用与卸载

临时停止使用“服务启停管理”。卸载先处理依赖当前网关的外部 WebDAV，再暂停调度并等待活动任务结束。

“卸载当前实例”明确选择保留全部数据，或再次确认删除当前实例数据。只移除核验过的本 Edition Bot、网关及无其他连接的自有网络；不执行全项目 `compose down`，不卸载 Docker／系统 Nginx，不操作另一 Edition。

完整清理先检查所有目录；遇到链接、跨文件系统、嵌套挂载、特殊对象或 CloudDrive2 非空挂载点即停止。清理仅限当前实例数据、配置、下载、日志及选定网关的数据，不遍历或删除云盘。公开部署包、操作记录、锁和独立导出的备份保留，便于检查和重新安装；不宣称整个主机恢复出厂状态。

## 发布和验收边界

一键脚本 helper A／入口 B、远端 CI、同 Tag 原生镜像和两版 format 3 包统一核验，真实状态见[发布记录](development/V158-ACCEPTANCE.md)。本地实现或文档出现不代表发布资产已齐，不混用旧 helper 与新包。

发布后分别在隔离的 Linux 主机检查新装、完整 format 2 保留数据升级、早期无 helper 包的安全停止、默认端口、认证隔离、实际限额、监听、家人授权、外部 WebDAV、备份回读、失败回退和单 Edition 卸载。真实 Telegram、两网关上传、公网 DNS／ACME 及长期负载必须实机验收，自动化模拟不替代这些结果。
