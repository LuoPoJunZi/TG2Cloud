# 从 TG115 迁移到 TG2Cloud

当前 Linux v1.4.0 **不提供 TG115 原地自动迁移**。已经是官方 TG2Cloud 的实例使用正常保留配置升级；旧 TG115 属于独立人工迁移范围。

## 目录与名称的变化

| Edition | 旧目录 | 新目录 |
| --- | --- | --- |
| CloudDrive2 | `/opt/tg115` | `/opt/tg2cloud-clouddrive2` |
| OpenList | `/opt/tg115-openlist` | `/opt/tg2cloud-openlist` |

TG2Cloud 使用独立容器、网络和备份目录。所选 Edition 尚无完整 TG2Cloud、但发现对应旧 TG115 目录或容器时，当前 CLI 会停止；早期 EXE 的“只提示继续”不能套用。不会自动覆盖、停止、移动或删除旧资源。

如果固定管理端口 19798/5244 被占用，或新目录/容器归属不明，部署会停止，不会自行抢占资源或随机换端口。

## 迁移前先处理这几件事

1. 在旧实例中处理完队列，记录需要保留的失败任务和下载文件。
2. 通过旧项目的备份方式保护配置、数据库、网关状态和必要文件。
3. 记录 WebDAV 根目录、相对子目录、用户权限和存储挂载关系。
4. 确认新旧实例不会同时长期使用一个 Bot Token。
5. 确认有明确的失败后返回旧实例的方案。

所有凭据与备份留在自己的私有环境，不能公开提交给维护者。

## 推荐：独立安装后验证

优先在独立 VPS 按 TG2Cloud 新目录部署，由本人重新配置存储授权和 WebDAV，完成真写验收与小文件测试。

验收前保留旧 VPS 和完整备份。新项目正常运行并不自动意味着旧队列已迁移；旧状态延续需要专门的迁移与验证计划。

## 必须复用同一 VPS 时

安排维护窗口，先完成旧实例备份与隔离迁移方案；当前脚本遇到对应旧身份会停止，即使端口已空闲也不表示可以接管。优先用独立主机验证，不能只处理端口就假设可以自动延续队列。

不要简单重命名旧目录、移动数据库，或者批量替换文件内的 `TG115` 字样来“绕过”检测。

:::warning 数据库文件名不是迁移入口
源码中的 `tg115.db`、部分 `TG115_*` 兼容别名仍可能保留，这是兼容和持久化边界，不表示可以直接复制旧数据库或把所有旧名称批量改掉。
:::

## 本机主机记录也需要重新核对

Linux 脚本直接在目标主机运行，SSH 是用户自行登录的方式，应通过服务商控制台核对主机指纹。`%APPDATA%\TG2Cloud-Deployer\known_hosts` 仅属于历史 Windows 部署器，不是 Linux 状态路径。

## 明确尚未验证的范围

仓库迁移文档未承诺旧 TG115 队列/状态的真实 VPS 迁移已经验收，也未承诺可直接复制 `.env`、`rclone.conf`、SQLite 或网关数据目录。需要延续这些状态时，先验证迁移方案，不要盲目覆盖。
