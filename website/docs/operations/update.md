# 升级与修改配置

重启服务、用当前载荷重建和安装新版本是不同操作。升级前备份配置、数据库、Session 和必要网关状态；不要先卸载，也不要同时启动使用同一 Bot Token 的第二个实例。

## 选择原部署方式

| 当前方式 | 升级入口 |
| --- | --- |
| 公网一键脚本 | 重新运行原 `install.sh`，选择 Edition → 1. 安装与升级 |
| 可信内网脚本 | 重新运行原 `install-lan.sh`，保留内网模式与地址 |
| 独立 Docker Compose | 按 [Compose 教程](/deploy/compose/)核对新包、镜像 digest、配置保留及备份 |

不要用一种部署方式接管另一种，也不把公网 HTTPS 实例改为内网 HTTP。官方基线、容器和安装目录无法核验时停止，不提供强制覆盖选项。

## Linux 脚本：保留配置升级

以 CloudDrive2 公网实例为例，先只读预检：

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/LuoPoJunZi/TG2Cloud/main/install.sh) --edition clouddrive2 --check
```

确认计划、容量和备份后运行原入口，再确认安装与升级：

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/LuoPoJunZi/TG2Cloud/main/install.sh) --edition clouddrive2
```

OpenList 改用 `--edition openlist`；内网改用 `install-lan.sh`。`--check` 不安装或升级；它仍需要读取公开 GitHub 元数据和源码。旧版本 Release 缺失、源码不符或网关镜像发生变化时保留当前服务，备份后单独核对可信基线，不能通过改版本号或删数据绕过。

## 哪些配置会保留

升级保留 `.env` 原始字节、业务数据库、Bot／个人 Session、下载与持久化网关数据。rclone 可能重新混淆同一密码，配置字节变化不等于改密；不要公开解混淆结果，混淆不是加密。

新安装使用 `data/tg2cloud.db`，已有唯一旧库继续原地使用。不要手工改名、创建第二个业务库或删 SQLite 旁文件。数据库 schema 和回退必须匹配代码，详见[备份恢复](/operations/backup/)。

## 下载新版不等于 VPS 已更新

管理工具、实例 Bot、共享代理和外部 WebDAV 离线工具分别核对。更新网站或只重启容器不会安装新版；通过 `tg2cloud` 查看所选实例的 Bot 与 CLI 实际版本，不用目标版本代替失败后的运行版本。旧工具须显式更新，外部 WebDAV 在主菜单 15 的子菜单单独升级。

## `manage.sh update` 做什么

```bash
bash /opt/tg2cloud-clouddrive2/manage.sh update
```

它使用当前主机已安装的载荷重建 Bot，不从 GitHub 获取新的产品源码，不替换 `.env`。OpenList 对应操作还会处理 Compose 已固定的网关镜像；同样不等于升级至任意最新源码。

## 安装与升级反馈

v1.4.4 增加了日志分类、逐项结果摘要与验收引导；须升级为匹配的离线工具后才生效。更新网站不会更新 VPS，旧 v1.4.3 工具不包含新增反馈。发布状态与实际资产以[下载页](/download/)为准。

`[信息]` 表示正常阶段进度，`[提醒]` 解释受管构建中匹配的 pip root、CA 合集、固定 UID 或推荐容量提示；未知 WARNING 标为 `[待核对]`，明确错误标为 `[错误]`。同类解释只出现一次，原日志保留并脱敏。是否成功仍由原命令退出码和完整成功标记决定，常见提醒不能掩盖后续错误。

确认执行后，摘要分别说明基础步骤、原 `.env` 字节保留、收到的数据库备份确认、代码／版本、Bot 健康和本机入口。没有执行的项目不勾选通过，缺少证据显示未核实；首次安装的升级前备份、内网的公网 HTTPS 等显示不适用。基础升级完成但 HTTPS 或 WebDAV 未通过时，报告停止阶段和已完成范围，不冒充整体成功或自动回退。目标版本不等于失败后实际运行版本。

入口通过后，自动读取一次所选 Bot 的本地业务就绪观察，命令设置 20 秒超时，超时后的终止清理沿用原有执行机制；不追加 Telegram／WebDAV 探测、不绕过冷却、不自动重启。缺失、过期、不兼容或读取失败只说明就绪未核实，不推翻已经确认的基础升级；用户中断时不追加读取。

```text
── 转存验收 ──

业务就绪：基础条件通过（最近观察，不代表写入）
WebDAV 写入与大小复验：未执行
实际 Telegram 转存：待人工验收
公网访问：待外部网络验收
```

以上为示意，不是实机结果。升级默认不额外询问或执行 WebDAV 写入；首次安装及显式 `--verify` 沿用原确认。按摘要进入“业务就绪检查”“WebDAV 验收”，再向 Bot 转发自有小文件，在官方云存储客户端核对结果。真实转存、外部网络／局域网其他设备访问始终单列；大小复验不是内容哈希或云盘官方最终入库。不会自动提交文件，也不增加人工打勾后冒充自动验证的记录。

不会新增主菜单项、Bot 命令、环境变量、依赖或数据库字段，不重复改已确认菜单、命名与传输逻辑；两个 Edition 与公网／内网使用同一汇总规则。只读预检、取消计划或只更新管理工具不会生成虚构的升级通过摘要。原有 `TG2CLOUD_*` 原始标记和失败退出码保留，见[日志排查](/faq/)与[维护](/operations/maintenance/)。

## HTTPS 续做与已有凭据

更新后管理入口有问题，进入 `tg2cloud` → **7. HTTPS 与管理**，先检查现有域名、DNS、证书、80/443 和代理，不先移除正常路由或重建网关。不同代理模式、续期责任与安全边界见[HTTPS](/deploy/domain-https/)。

只查看已保存凭据进入 **6. WebDAV 凭据**，在私有终端确认后显示。OpenList 保存的初始化密码可能已在后台修改；查看操作不重置管理员账号。

## 单独应用配置

先保存私有备份，按[配置参考](/reference/config/)核对确需变更的值，再在维护窗口应用并重建所选 Bot；只改本地记录或 restart 不保证新环境变量已进入容器。保持目录、网关账号和 Bot 凭据对应，不把管理域名作为内部 WebDAV 地址。

## 升级后检查清单

1. Bot 与 CLI 显示真实版本，运行代码和基础健康检查通过。
2. 原 `.env`、数据库、Session 和必要备份仍可核验。
3. 运行一次业务就绪检查，确认不是过期观察。
4. 明确确认后执行 WebDAV 写入、大小复验及受限测试对象清理。
5. 向 Bot 转发自有小文件，在目标网盘确认可打开；公网从外部网络、内网从其他局域网设备访问。
6. 核对共享代理另一 Edition 和只读入口正常，后续再安排续期与隔离恢复演练。

实际版本证据及未运行场景见[当前记录](https://github.com/LuoPoJunZi/TG2Cloud/blob/main/docs/development/V153-ACCEPTANCE.md)。升级成功不等于云盘官方最终入库或完整灾难恢复通过。
